# BROV Sim2Real 작업 기록 — 2026-08-13

## 목적

BlueROV2 실기체에서 발생한 불안정 동작의 원인을 다음 세 영역으로 분리해 검증했다.

1. MAVLink 텔레메트리와 16차원 observation
2. action → wrench → T1~T8 PWM 전달 경로
3. 학습 정책 자체의 출력 특성

## Observation 및 policy 실측

시험 설정:

```text
waypoints=0,0,0;0.5,0,0
waypoint_frame=start_heading
heading_mode=straight
cruise_speed=0.1 m/s
```

관련 토픽은 약 25 Hz로 발행됐으며 당시 대표 observation은 다음과 같았다.

```text
attitude error RPY ≈ [roll +0.97°, pitch -5.14°, yaw -0.10°]
velocity error      ≈ [-0.096, +0.021, +0.009] m/s
```

동일 observation에 대한 policy 출력:

```text
action = [surge +0.207, sway +0.308, heave +0.063,
          roll -0.028, pitch -0.484, yaw +0.055]
pitch torque ≈ -6.77 Nm
```

합성 입력 검사에서도 다음 특성이 재현됐다.

```text
완전 무오차:         sway action ≈ +0.232
pitch error -5.14°: pitch action ≈ -0.483
pitch error +5.14°: pitch action ≈ +0.477
```

정책은 정상상태 sway bias가 있고 작은 pitch 오차에도 매우 강한 응답을 보였다.

## 카메라 틸트 변경과 추진기 매핑 재검증

카메라 tilt는 별도 `MAV_CMD_DO_MOUNT_CONTROL` 경로를 사용하므로 observation을
직접 변경하지 않는다. 틸트 충돌 제거와 함께 추가했던 T2/T3/T8 PWM 반전이 실제
운동과 일치하는지 `diag_thruster_map.py`로 다시 검사했다.

### Neutral 및 전기 출력

```text
mode=MANUAL(19), armed=False
T1~T8 neutral=1500 us: OK
T1~T8 ±40 us: 모두 DIRECT
채널 간 교차 출력: 없음
```

### 실제 운동 방향

| Thruster | 판정 | production sign |
|---|---:|---:|
| T1 | NORMAL | +1 |
| T2 | REVERSED | -1 |
| T3 | REVERSED | -1 |
| T4 | NORMAL | +1 |
| T5 | NORMAL | +1 |
| T6 | NORMAL | +1 |
| T7 | NORMAL | +1 |
| T8 | REVERSED | -1 |

실측 반전 마스크는 코드와 일치했다.

```text
[+1, -1, -1, +1, +1, +1, +1, -1]
```

따라서 채널 매핑과 T2/T3/T8 반전은 불안정 동작의 주원인이 아닌 것으로 판단했다.

### 잔류 ArduSub 설정

진단 시작 전부터 다음 설정이 남아 있었다.

```text
SERVO1~3_FUNCTION = 33,34,35
SERVO4~8_FUNCTION = 1 (RCPassThru)
RC7_OPTION = 0
RC8_OPTION = 0
```

이전 `obs_node`가 정상 종료되지 않아 복원이 끝나지 않은 것으로 추정된다. 직접 RL
제어 중에는 전 채널을 다시 RCPassThru로 사용하지만, 비정상 종료 후 ArduSub 기본
mixer와 RC camera 기능이 복원되지 않는 문제는 별도로 보완해야 한다.

## Model-based controller 구현

정책을 완전히 우회하고 동일 observation/PWM 경로를 검증하기 위해 명시적
PI/PD controller를 구현했다.

관련 파일:

- `model_based_controller.py`
- `ros2_nodes/model_based_controller_node.py`
- `test_model_based_controller.py`
- `MODEL_BASED_CONTROL.md`

제어 구조:

```text
16-dim observation
→ velocity PI + attitude/rate PD
→ Z-up/FLU wrench
→ SNAME/FRD wrench 변환
→ B pseudo-inverse allocation
→ T200 inverse model
→ T1~T8 PWM
```

제어식:

```text
Force  = -Kp_v * v_e - Ki_v * z_v
Torque = -Kp_q * rotation_vector(q_e) - Kd_w * omega - Ki_q * z_q
```

안전 기능:

- 기본 preview-only
- `/brov/control_active=false`이면 enable 거부
- 경쟁 `/brov/thruster_pwm` publisher가 있으면 enable 거부 또는 자동 중지
- observation watchdog
- stop 및 활성 상태 `Ctrl+C` 종료 시 neutral PWM 발행
- quaternion shortest-rotation 처리
- wrench/PWM limit

## T200 deadband 문제와 수정

초기 model controller의 대표 PWM은 다음과 같았다.

```text
[-0.094, -0.001, +0.056, -0.039,
 -0.039, -0.010, -0.015, -0.002]
```

T200 모델은 `|PWM| <= 0.075`에서 추력이 0이므로 T1을 제외한 대부분의 추진기가
실제 힘을 만들지 않았다. 서비스 및 PWM topic은 정상이어도 목표 wrench가 실현되지
않는 상태였다.

다음 deadband-aware 처리를 추가했다.

```text
|requested thruster force| < 0.25 N → PWM 0
활성 thruster                       → 최소 |PWM|=0.10
```

수정 후 preview와 실제 `/brov/thruster_pwm`에서 여러 채널의 `±0.10` 이상 출력을
확인했다. 요청 wrench와 deadband/추진기 지연을 반영한 예상 wrench는 각각 다음
토픽으로 확인한다.

```text
/brov/model_based/wrench_zup
/brov/model_based/estimated_wrench_zup
```

## Quaternion observation 결함과 수정

실제 observation에서 다음 값이 확인됐다.

```text
q_e = [-0.9988, -0.0077, +0.0458, +0.0148]
```

이는 물리적으로 부호를 반전한 작은 자세 오차 quaternion과 동일하지만, 신경망에는
`q_e ≈ [-1,0,0,0]`이라는 전혀 다른 숫자로 입력된다. 이 불연속은 기존 policy의
오작동을 설명할 수 있는 유력한 observation 결함이다.

`q_e.w < 0`이면 quaternion 전체 부호를 반전하여 항상 다음 조건을 만족하도록
수정했다.

```text
q_e.w >= 0
```

추가한 observation/PWM 검증 토픽:

```text
/brov/debug/pos_mission
/brov/debug/v_body_zup
/brov/debug/v_desired_body_zup
/brov/debug/servo_output_us
```

관련 controller 및 quaternion 회귀 테스트는 총 6개가 통과했다.

## 상승 waypoint 시험

시험 경로:

```text
0,0,0
0,0,-0.6
1,0,-0.6
1,0.4,-0.6
0,0,-0.6
0,0,0
```

`start_heading`에서도 Z축은 NED이므로 `z=-0.6`은 0.6 m 상승 목표가 맞다. 수직
추진기는 동작했지만 기체가 상승하지 않았다.

초기 `Kp_z=35`에서는 목표 상승속도 오차 0.1 m/s에 약 3.5 N만 요청하므로 실제
음성부력, ballast 또는 tether 하중을 이기지 못했을 가능성이 있다.

다음 P-only 설정으로 단계적 시험을 진행한다.

```bash
python3 model_based_controller_node.py --ros-args \
  -p linear_kp:="[25.0, 25.0, 100.0]" \
  -p linear_ki:="[0.0, 0.0, 0.0]" \
  -p force_limit:="[15.0, 15.0, 15.0]" \
  -p minimum_active_pwm:=0.10
```

`Kp_z=100`일 때 상승속도 오차 0.1 m/s에 대한 계산값:

```text
requested Z-up force ≈ +10 N
T5/T6 logical PWM    ≈ -0.150
T7/T8 logical PWM    ≈ -0.168
estimated Z-up force ≈ +10 N
```

이후 `0,0,0;0,0,-0.5`뿐 아니라
`0,0,0;0,0,-0.5;1,0,-0.5` 경로에서도 초기 상승 뒤 하강하는 현상을 추가 분석했다.
원인은 단순 heave gain 부족이 아니라 guidance 구조였다.

```text
첫 depth waypoint의 reach radius 조기 진입
→ 수평 segment로 전환
→ 1 m 수평 LOS가 depth 오차를 압도
→ 수직 목표속도 감소
→ 음성부력/tether 외력에 의해 하강
```

또한 마지막 waypoint에서 `mission_complete=True`가 되면 목표속도를 0으로 고정해,
외력으로 목표점에서 이탈해도 복귀하지 못했다.

다음과 같이 수정했다.

- 수평 LOS와 depth position outer-loop 분리
- 모든 segment에서 다음 waypoint Z를 독립 추종
- 마지막 waypoint 도달 후 terminal 3D position hold 지속
- `mission_complete`는 도달 이력으로만 사용

관련 guidance/controller/quaternion 회귀 테스트는 총 8개가 통과했다.

실제 ballast/tether 조건에 따라 heave gain 또는 적분/feedforward의 추가 조정은
필요할 수 있다. `Kp_z=100`에서 부족하면 `Kp_z=150`으로 올리되
`force_limit_z=15 N`은 유지한다. 15 N에서도 상승하지 않으면 gain이 아니라 다음
항목을 조사한다.

- 실제 부력 및 ballast
- tether 하중
- 수직 추진기 합력 방향과 실제 추력
- ESC 상태
- DVL/depth 위치 추정

## ROS 2 package 및 bringup 이관

기존에 `python3 ros2_nodes/*.py`로 각각 실행하던 구조를 ROS 2 Humble package와
launch 기반으로 이관했다. 검증된 제어 구현은 변경하지 않고 console entry point가
기존 `deploy.*` 모듈을 호출하도록 구성했다.

```text
brov_base        obs/MAVLink/guidance/PWM gateway
brov_control     model-based 및 RL controller
brov_perception  camera/calibration/ArUco
brov_bringup     config와 launch 조합
```

추가한 launch:

```text
base.launch.py
model_demo.launch.py
rl_demo.launch.py
camera.launch.py
sim2real_demo.launch.py
```

안전 기본값은 `send_pwm=false`, `arm=false`이며 어떤 launch도 control start service를
자동 호출하지 않는다. full demo는 `controller:=model|rl` 중 하나만 생성한다.
Docker shell은 `/workspace/deploy/ros2_ws/install/setup.bash`를 자동으로 source하며,
`make ros-build`, `make ros-test`, `make check`로 build/회귀/환경 검사를 수행한다.

검증 결과:

```text
colcon build:                 4 packages passed
launch --show-args:           5/5 passed
installed executables:        6 discovered
YAML parsing:                 6/6 passed
control regression tests:     8 passed
environment/package check:    all passed
```

현재 package는 1차 이행 구조이므로 Compose의 `/workspace/deploy` bind mount와
`PYTHONPATH=/workspace`가 필요하다. 독립 설치 가능한 package로 만들기 위한 핵심 구현,
vendor YAML 및 asset 이관은 후속 범위다. rosbag 자동 기록 옵션도 아직 남아 있다.

## 현재 결론 및 다음 확인 항목

1. T1~T8 채널과 반전 마스크는 실기체와 일치한다.
2. 기존 정책에는 큰 sway bias와 높은 pitch gain이 있다.
3. observation에 실제 quaternion 부호 불연속 문제가 있었으며 수정했다.
4. model-based controller와 PWM 발행 경로를 구현했다.
5. 초기 무동작은 T200 deadband 처리 누락이 원인이었으며 수정했다.
6. 수평 segment/미션 완료 후 depth hold가 사라지던 guidance 문제를 수정했다.
7. 실기체 정적 하중에 대한 heave gain·integral·feedforward 조정은 후속 과제다.
8. 다음 실험에서는 `servo_output_us`, `pos_mission`, 실제/목표 body velocity 및
   requested/estimated wrench를 동시에 기록한다.
